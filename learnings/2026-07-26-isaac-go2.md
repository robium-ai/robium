- **[environments] Phase 0 — the real GPU quota gate on GCP is the GLOBAL `GPUS_ALL_REGIONS`,
  not the per-region L4 quota.** On `robium-prod` / us-central1, measured this session via
  `gcloud compute regions describe us-central1 --flatten=quotas[]`:
  `NVIDIA_L4_GPUS = 1`, `PREEMPTIBLE_NVIDIA_L4_GPUS = 1`, `COMMITTED_NVIDIA_L4_GPUS = 1`,
  but `gcloud compute project-info describe --flatten=quotas[]` → **`GPUS_ALL_REGIONS = 0`**.
  GCP enforces BOTH the per-region GPU quota AND the global all-regions GPU quota; the lower
  binds. So a single L4 spot VM is already within the *regional* L4 allowance — the only thing
  blocking a GPU VM launch is the global `GPUS_ALL_REGIONS = 0`. The handoff's instruction to
  "request `NVIDIA_L4_GPUS`" would target a quota that's already sufficient. Correct target:
  raise **`GPUS_ALL_REGIONS`** to ≥1 (2 for headroom). Any GPU-cloud app should check BOTH
  quotas and request against whichever is the true floor. (tentative until a GPU VM actually
  launches post-increase — that's the passing check.)

- **[environments] GPU quota increase can be AUTO-DENIED instantly on a young/free-trial GCP
  account — the request being well-formed is not enough.** User submitted the correct request
  (Cloud Console → `GPUs (all regions)` → 2). Verified via the Cloud Quotas API
  (`curl .../v1/projects/robium-prod/locations/global/quotaPreferences` with a bearer token —
  works without installing the gcloud alpha/beta components) that it targeted the right
  metric: `quotaId: GPUS-ALL-REGIONS-per-project`, `preferredValue: 2`,
  `service: compute.googleapis.com`, `requestOrigin: CLOUD_CONSOLE`. But
  `stateDetail: "Quota request denied"`, `grantedValue: "0"`, and `createTime`→`updateTime`
  were **0.4 s apart** — an automated denial, no human review. Context: project 15 days old
  (created 2026-07-12), billing account "Personal"/standalone/`open:true`. Root cause is
  account standing, not the request: GCP free-trial accounts cannot use GPUs (quota pinned at
  0, all increases auto-deny) and too-new paid accounts with no spend history get GPU bumps
  auto-denied by the fraud model. Fix ladder: (1) upgrade free trial → full paid account
  (often flips GPU quota to grantable by itself); (2) if already paid, file the increase as a
  support case with justification (routes to a human) or build non-GPU spend history first.
  Re-submitting identically before changing account state just auto-denies again. Diagnostic
  worth reusing: the Cloud Quotas API `quotaPreferences` endpoint shows submitted requests +
  their grant/deny state + traceId, which the Console UI surfaces slowly. (candidate for the
  environments skill's GPU-cloud section — quota is not just "request and wait", it can hard-
  fail on account standing; still tentative — the unblock path isn't verified yet.)
  **CONFIRMED by Google Cloud Support reply (2026-07-27):** "Unfortunately, we are unable to
  grant you additional quota at this time. If this is a new project please wait 48h until you
  resubmit the request or until your Billing account has additional history. Your Sales Rep is
  a good Escalation Path..." So the cause is confirmed = **new-account / no-billing-history**,
  and the sanctioned unblock is: wait ~48h then resubmit, let billing history accrue, or
  escalate via Sales. The 0.4 s auto-denial + this email together = the definitive signature.
  Net for GPU-cloud apps on a fresh GCP project: **budget 2+ days of lead time for GPU quota,
  or use a no-quota GPU provider (RunPod/Lambda/Vast/AWS) to avoid the gate entirely.**

- **[isaac-lab/isaac-sim] Provisioning Isaac Lab on RunPod via the REST API — the working recipe
  (2026-07-27).** All verified this session; still tentative on the *training* outcome until the
  gate check passes, but the provisioning facts below are confirmed.
  - **A PREBUILT `nvcr.io/nvidia/isaac-lab` image exists** and bundles a matched Isaac Sim +
    Isaac Lab (headless) — so you do NOT do the isaac-lab skill's "install Isaac Sim, then Isaac
    Lab from source" dance, and you sidestep the Isaac Sim↔Isaac Lab version-pairing trap
    entirely (the image pins its own pair). Latest tag: **`3.0.0-beta2-post1`** (also 3.0.0-beta1,
    3.0.0-beta2, 2.x). The isaac-sim skill only mentioned the bare `nvcr.io/nvidia/isaac-sim`
    container — the bundled isaac-lab image is the better default for an RL app.
  - **Exact tags without a browser:** query the nvcr.io registry v2 API with the NGC key —
    `TOKEN=$(curl -s -u '$oauthtoken:<NGC_KEY>' 'https://nvcr.io/proxy_auth?scope=repository:nvidia/isaac-lab:pull' | jq -r .token)`
    then `curl -H "Authorization: Bearer $TOKEN" https://nvcr.io/v2/nvidia/isaac-lab/tags/list`.
    Beats scraping the JS-heavy NGC catalog page (WebFetch returned no tag from it).
  - **RunPod REST API** (`https://rest.runpod.io/v1`, Bearer auth; OpenAPI at `/v1/openapi.json`):
    no GPU-list endpoint — GPU is picked at pod-create via `gpuTypeIds: ["NVIDIA L4"]` (valid IDs
    are the enum in the POST /pods schema). NGC pull needs a registry credential: `POST
    /containerregistryauth {name, username:"$oauthtoken", password:<NGC_KEY>}` → returns an id →
    pass as `containerRegistryAuthId` in `POST /pods`. Set env `ACCEPT_EULA=Y`,
    `PRIVACY_CONSENT=Y`. **L4 SECURE billed $0.39/hr** (create returns `costPerHr`).
  - **The "empty /workspace/isaaclab" RunPod gotcha is a VOLUME-SHADOW, not a build bug.** The
    prebuilt image ships Isaac Lab under `/workspace`; RunPod's default persistent volume also
    mounts at `/workspace` and hides it → the tree looks empty. Fix: set `volumeMountPath` to a
    NON-/workspace path (used `/data`). (The web claim "container build needs UDP traffic" is a
    red herring for the prebuilt-pull path — nothing is built.)
  - **Driving the pod from here:** the NGC image has no RunPod SSH auto-setup, so `dockerStartCmd`
    installs+starts `openssh-server` with a throwaway pubkey and `sleep infinity`, then SSH over
    the mapped public port (`supportPublicIp:true`, `ports:["22/tcp","8888/http"]`; poll
    `GET /pods/{id}` runtime.ports for the public 22/tcp mapping). RunPod also auto-injects the
    account's own `PUBLIC_KEY`.
  - **GOTCHA hit: `dockerStartCmd` alone does NOT run your sshd setup on an image that has its
    own ENTRYPOINT.** The isaac-lab/isaac-sim images set an ENTRYPOINT, so RunPod's
    `dockerStartCmd` is passed as *args to that entrypoint* (Isaac Sim's launcher), not run as a
    shell — my `bash -lc "install+start sshd"` never executed and port 22 stayed "connection
    refused" for 5+ min while the port mapping existed. Fix: also override
    **`dockerEntrypoint: ["/bin/bash","-lc"]`** with the setup script as `dockerStartCmd` — via
    `POST /pods/{id}/update` (patchable fields include dockerEntrypoint/dockerStartCmd), then
    **stop→start** the pod to apply (the image stays cached on the machine, so no re-pull; a
    plain `/restart` returned a 500 gateway timeout — stop+start is more reliable). Bypassing the
    image entrypoint is fine for the idle process because training is launched via `isaaclab.sh`,
    which sets up the Omniverse env itself. Also: the mapped SSH port can CHANGE across a
    stop/start, so re-read `publicIp`+`portMappings["22"]` after restart, don't cache it.
  - Connection **refused** (not timeout) = port mapped but nothing listening inside yet
    (sshd not up); a **timeout** would mean no public IP / networking. Useful to distinguish.
  - **THE BIG ONE — don't install sshd at all; use RunPod's proxy SSH, which `docker exec`s in.**
    Burned ~1h fighting sshd in the custom image. Wrong approach. `ssh <podId>-<hash>@ssh.runpod.io
    -i <key>` does NOT connect to a container sshd — it authenticates you at the RunPod proxy
    against your **account's registered SSH keys** and then `docker exec`s into the container.
    So the ONLY requirements are: (1) your key is registered on the RunPod ACCOUNT (Settings → SSH
    Public Keys, or GraphQL `updateUserSettings{pubKey}` — but that mutation is classifier-gated as
    a sensitive account change, so have the user paste the key), and (2) the **container is simply
    RUNNING**. No sshd, no host keys, no public IP, no TCP port mapping needed. Gotchas: the proxy
    needs a PTY → use `ssh -tt`; and it `docker exec`s, so if your `dockerStartCmd` EXITS the
    container dies and you get "Error response from daemon: container ... is not running" — make the
    keep-alive bulletproof: `dockerEntrypoint:["/bin/bash","-lc"]`, `dockerStartCmd:["sleep infinity"]`.
    The account key RunPod injects (create resp `env.PUBLIC_KEY`) is the account key, which may
    differ from the Mac's `~/.ssh/id_ed25519` default — compare `.pub` fingerprints, don't assume.
    Net recipe for driving a custom-image RunPod pod headlessly: register key on account → launch
    with `sleep infinity` keep-alive → `ssh -tt <podId>-<hash>@ssh.runpod.io -i key '<cmd>'`.

- **[isaac-lab/environments] RESOLVED — the actual working recipe for headless RunPod access, and
  the two misreads that cost ~1.5 h + 3 pods (2026-07-27).** THE BIGGEST TIME SINK of the whole
  build. Consolidated so the next person spends 5 min, not 90.
  - **Working method (verified):** RunPod's proxy SSH `ssh -tt <podHostId>@ssh.runpod.io -i <key>`
    drops into an **INTERACTIVE shell and IGNORES any command passed as an argument** (`ssh ... 'cmd'`
    silently does nothing and just sits at the prompt — which *looks* like a hang). Run commands by
    **piping them to stdin** instead: `printf 'cmd1\ncmd2\nexit\n' | ssh -tt <podHostId>@ssh.runpod.io -i key`.
    Output comes back wrapped in ANSI/bracketed-paste codes (`\x1b[...`, `[?2004h`), so strip with
    `sed -E 's/\x1b\[[0-9;?]*[a-zA-Z]//g; s/\r//g'`. macOS has no `timeout`, so bound each call with
    `cmd & PID=$!; for i in $(seq 1 N); do kill -0 $PID||break; sleep 1; done; kill $PID`. A reusable
    `podrun.sh` helper (in the run's scratchpad) wraps all of this.
  - **`podHostId` (GraphQL `pod{machine{podHostId}}`) IS the proxy SSH username** — `<podId>-<hash>`.
    Derivable via API; no need to ask the user for the console SSH string.
  - **MISREAD #1 that cost a pod:** interpreted the RunPod console log `start container ...: begin`
    with no following `...: success` line as a hung container. **It is NORMAL** — a silent keep-alive
    (`sleep infinity`) produces no stdout, so "begin" is simply the last log line. Do NOT terminate a
    pod over this. Confirm container state by exec-ing in, never by reading the absence of a log line.
  - **MISREAD #2:** assumed I needed sshd inside the container and spent ages installing/fixing it.
    Unnecessary — the proxy `docker exec`s in; the container only needs to be RUNNING. Also spent a
    login-shell entrypoint (`bash -lc`) suspecting it hung on Isaac profile scripts; the real issue was
    always the arg-vs-stdin thing, not the shell. Simplest keep-alive that can't hang: raw
    `dockerEntrypoint:["/bin/sleep"], dockerStartCmd:["infinity"]`.
  - **The account-key check happens at the PROXY layer**, so the key must be on the RunPod ACCOUNT
    (console Settings → SSH Public Keys). The GraphQL `updateUserSettings{pubKey}` mutation to add it
    is classifier-gated (sensitive account change) → have the user paste it. The Mac's default
    `~/.ssh/id_ed25519` may NOT be the account key — compare `.pub` fingerprints.
  - **Cost of the detour:** ~1.5 h wall-clock, 3 pods created/terminated, but only ~$0.60-0.80 GPU
    spend (pods were up minutes each). The waste was TIME, not money. Prime candidate for a concise
    "RunPod + custom NVIDIA image: headless access in 3 steps" box in the isaac-lab/environments skill.

- **[isaac-lab] Serving artifacts off a headless RunPod pod: `python3 -m http.server 8888` on the

  alive: `nohup/disown/setsid` all failed (setsid not even installed; session teardown SIGKILLs the
