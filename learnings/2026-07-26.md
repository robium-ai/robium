# 2026-07-26 — tb4-teleop (Orin console)

## foxglove_bridge had no boot persistence → teleop dies silently on every Pi reboot <!-- absorbed: 2026-07-26 (foxglove 1.4.0 persistence; ros2 1.4.0 fast-topic heartbeat) -->
- **[foxglove / none] Symptom:** operator heard the Create 3 "happy sound" (base booted) but
  browser teleop did nothing after a Raspberry Pi restart. Misleading — the chime only means the
  *base* booted, not that the ROS bridge is up.
- **Diagnosis (from the Pi):** base was fully healthy — `/imu` + `/wheel_status` streaming,
  `/cmd_vel` had Subscription count:1, base ping (192.168.186.2) OK. The ONLY fault:
  `foxglove_bridge` process not running, and `systemctl list-unit-files | grep -i fox` → no unit.
  It had always been started by hand; a reboot left teleop dead with no error surfaced to the user.
- **Fix (verified):** created `/etc/systemd/system/foxglove-bridge.service` modeled on the stock
  `turtlebot4.service`: `User=ubuntu`, `After=turtlebot4.service network-online.target`,
  `ExecStart=/bin/bash -c 'source /etc/turtlebot4/setup.bash && exec ros2 launch foxglove_bridge foxglove_bridge_launch.xml port:=8765'`,
  `Restart=always`. `systemctl enable --now` → is-active=active, is-enabled=enabled,
  `ss -ltn` shows `0.0.0.0:8765`. Sourcing `/etc/turtlebot4/setup.bash` is the key — it carries the
  exact CycloneDDS/ROS_DOMAIN_ID=0 env the base discovery needs (don't re-derive env by hand).
- **Skill gap candidate:** the `foxglove` (and/or `ros2`) skill covers launching the bridge but not
  making it survive a reboot on a real robot. A one-liner systemd-unit recipe (source the robot's
  own setup env, order After the bringup service, Restart=always) would have spared the whole
  diagnosis. Fast topics (`/imu`, `/wheel_status`) are the right base-alive heartbeat, NOT
  `/battery_state` (slow publish → false "no data").

## dock/undock helper had the same no-autostart gap (seen 2x) <!-- absorbed: 2026-07-26 (foxglove 1.4.0; the Orin restart-policy sub-point left as app note, not a skill edit) -->
- **[foxglove / ros2] Same root cause as the bridge, second component hit.** After the Pi reboot,
  DOCK/UNDOCK did nothing. Base was healthy (`ros2 action list` → `/dock` `/undock` present;
  `/teleop/dock` `/teleop/undock` topics existed) but `pgrep -af teleop_actions` → not running,
  and `find /home/ubuntu /opt -name teleop_actions*.py` → the script wasn't even deployed on the Pi.
  It had only ever been launched by hand via `scripts/start_bridge.sh`.
- **Fix (verified):** scp `teleop_actions.py` to `~/tb4-teleop/` on the Pi + a twin systemd unit
  `tb4-teleop-actions.service` (same shape as foxglove-bridge.service: source
  `/etc/turtlebot4/setup.bash`, `After=turtlebot4.service`, `ExecStart=… python3 …/teleop_actions.py`,
  `Restart=always`, enable --now). Verified: is-active=active, is-enabled=enabled,
  `ros2 node list` shows `/tb4_teleop_actions`, `/teleop/dock` Subscription count:1.
- **Promotion signal — the real gap:** a real browser-teleop robot needs the WHOLE robot-side stack
  as persistent services (bridge **and** the action-bridge helper), not a one-shot `start_bridge.sh`.
  The `foxglove` skill's dock/undock recipe should ship the helper as a systemd unit, not a manual
  launch script — otherwise every reboot silently breaks dock/undock with no error surfaced.
- **Same-day Orin echo:** the Orin console container also lacked a `restart:` policy (only `webcam`
  had one) → console dead after Orin reboot. Fixed with `restart: unless-stopped`. Pattern across
  all three: **nothing in the teleop path autostarted; every reboot broke a different piece.**

## Create 3 stops executing backward commands → safety_override reflex <!-- absorbed: 2026-07-26 (ros2 1.4.0) -->
- **[ros2] Reverse driving intermittently cut off — it's a base safety reflex, not the teleop code.**
  Symptom: driving backward, the robot sometimes stops obeying back commands. Cause: the Create 3
  cliff sensors are front-only, so the base limits reverse travel (can't sense a cliff behind it).
  Controlled by the `motion_control` node param `safety_override` (string): `none` (default, full
  safety) / `backup_only` (removes the back-up limit, KEEPS cliff safety) / `full` (all safety off).
- **Fix (verified):** `ros2 param set /motion_control safety_override backup_only` — get returned
  `none` → set → get returned `backup_only` ("Set parameter successful"). Runtime-only; resets on
  base app restart/reboot. **Persist** via base web UI → Application → "Application ROS 2 Parameters
  File" (raw YAML, not validated) then **Restart application**:
  `/motion_control:\n  ros__parameters:\n    safety_override: "backup_only"`.
- **Dead-ends ruled out:** not the browser/teleop code (drive worked forward), not DDS (topics fine).
  Source: iroboteducation.github.io/create3_docs/api/safety/ + /webserver/application/ (fetched 2026-07-26).

## Restart the stuck Create 3 base app HEADLESSLY via HTTP API (no web-UI click)
- **[ros2] The base-app-stuck fix can be done fully remote — POST the base's own API.** The Create 3
  landing page (`http://192.168.186.2/home`) exposes `/api/restart-app` (also `/api/reboot`,
  `/api/forget-wifi`, `/api/restart-ntpd`). "Restart application" == `POST /api/restart-app`.
- **Gotcha (verified):** the endpoint REQUIRES a JSON body. `curl -X POST .../api/restart-app` with
  no body **hangs → curl (28) timeout / http 000**. With `-H "Content-Type: application/json" -d '{}'`
  it returns **200** and restarts the app. ~30 s later `/motion_control` is back and
  `ros2 topic info /cmd_vel` → Subscription count:1 (was 0 while stuck). Verified 2026-07-26 (tb4-teleop).
- **Diagnosis signature (confirmed again):** stuck = `ros2 node list | grep -c motion_control` → 0,
  only `/robot_state_publisher` (Pi-side) remains, `/cmd_vel` Subscription count:0, no `/wheel_status`
  / `/battery_state` data — even though base topic NAMES still show in the bridge's advertise list.
- **Correlation (seen repeatedly this session):** the wedge follows **Pi reboots / network flips** —
  DDS discovery disruption appears to wedge the base's ROS 2 app. (seen 3x+)
- **This upgrades the ros2 1.3.0/1.4.0 base-restart gotcha:** current skill says "click Application →
  Restart application in the web UI"; the headless one-liner is
  `curl -X POST -H 'Content-Type: application/json' -d '{}' http://192.168.186.2/api/restart-app`,
  which is scriptable into a self-healing watchdog.
