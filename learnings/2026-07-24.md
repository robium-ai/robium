# 2026-07-24 — tb4 teleop (real-hardware bring-up, pre-app)

Context: new app kickoff — real TurtleBot 4 (Create 3 + RPi 4, ROS 2 Humble), teleop
demo page, navigation-first. Long hardware/network bring-up before any app code. No
robium skill covers real-robot network bring-up — logging as a gap.

- [none] No skill fired for **connecting to a headless robot with no shared network**.
  Figured out from scratch: robot + Mac not co-networked, no screen. Working method:
  direct Ethernet cable → the robot's **IPv6 link-local** address is discoverable via
  `ping6 -c ff02::1%<iface>` then read `ndp -a`; SSH over `ubuntu@fe80::...%en5`. macOS
  Internet Sharing bridge is `bridge100`/`192.168.2.1`; its absence = sharing not active.
  Candidate skill: an `environments`/robot-networking reference for first-contact with
  headless hardware. (seen 1x)

- [none] No skill fired for **TB4 "zero ROS topics" root cause**. Symptom: `ros2 topic
  list` empty, `turtlebot4.service` FAILED with `rcl node's rmw handle is invalid, at
  ./src/rcl/node.c:415`. Root cause: robot never joined Wi-Fi → `wlan0` DOWN, and
  `/etc/turtlebot4/cyclonedds_rpi.xml` binds CycloneDDS to **`wlan0` only** (usb0
  commented out). No usable DDS interface → node creation fails → service dies → no
  topics. Fix: join Wi-Fi; everything cascades back. Verified: after `wlan0` got an IP,
  `systemctl restart turtlebot4.service` → active, 24 topics. This is a high-value,
  non-obvious diagnostic chain (service failure looks unrelated to Wi-Fi).

- [none] TB4 Wi-Fi reconfig method (figured from scratch): config lives in
  `/etc/netplan/50-wifis.yaml` (renderer NetworkManager, "created by turtlebot4-setup,
  do not edit" — but direct edit + `netplan generate`/`apply` works). Robot was
  configured for an out-of-range SSID (`RobotWiFi-EXT`); rewrote to the in-range one
  (`RobotWiFi`, 2.4GHz), `chmod 600` (netplan warns on world-readable), applied
  **detached via nohup** so the eth0-bounce during apply doesn't kill the SSH session.
  Result: `wlan0` connected, `192.168.0.100`, `autoconnect: yes` (persists reboots).

- [none] **DDS-across-NAT insight** (design-shaping): feeding the isolated RobotWiFi
  router internet by cabling Mac→router **WAN** + macOS Internet Sharing works for
  internet, BUT puts the Mac on the WAN side behind NAT — ROS 2 DDS **multicast
  discovery does not cross NAT**, so the Mac sees zero topics. For teleop the Mac MUST
  be on a **LAN** port (same subnet as robot). Either/or with one cable: LAN=topics /
  WAN=internet. Robot needs no internet for nav teleop; clock fixed locally via
  `sudo date -u -s "<mac UTC>"` over SSH (no NTP needed).

- [none] macOS constraint (relevant to teleop arch): no native ROS on macOS, and Docker
  Desktop's VM breaks DDS multicast to the physical LAN (same class of issue nav-trial
  documented). Implication: the ROS↔browser **bridge must run ON the robot** (localhost
  DDS), browser connects over TCP WebSocket. Neither `rosbridge_server` nor
  `foxglove_bridge` is installed on the robot yet (install needs a one-time internet
  path).

## Bridge install (Task 0) — plan said cable+Internet Sharing; that failed, pivoted

- [none] **macOS Internet Sharing from an iPhone hotspot would not activate.** Toggled it
  twice; `bridge100`/`192.168.2.1` never came up, and the half-on state *broke the cable
  link* (Pi answered IPv6 multicast but unicast SSH timed out — ND resolution failing).
  Turning Sharing OFF restored the cable. Dead-end ruled out: it's not the cable/port
  (link `active`, 1000baseT) — macOS simply refuses to NAT-share a tethered hotspot
  uplink here. The spec's chosen install path (§7) is therefore unreliable on this setup.

- [none] **IPv6 link-local over the direct cable is intermittently flaky** for unicast
  SSH (multicast ping works, `ndp` entry expires, unicast times out) — recurred all
  session. **Fix that stuck: add an IPv4 alias on the Mac in the Pi's static-eth0 subnet**
  — `sudo ifconfig en5 inet 192.168.185.10 netmask 255.255.255.0 alias` (Pi eth0 is a
  static `192.168.185.3`), then `ssh ubuntu@192.168.185.3`. IPv4/ARP held far better than
  IPv6/ND. Even so it dropped under sustained load (apt), so:

- [none] **Working install method (replaces spec §7):** keep the cable as an out-of-band
  *management* channel; temporarily join the robot's **wlan0 to a phone hotspot with
  internet** (`nmcli dev wifi rescan` first — the scan goes stale and the SSID won't be
  found otherwise), run `apt-get install` **detached via `nohup`** writing a
  `DONE_RC=$?` marker (so SSH drops don't abort it), poll the marker, then
  `nmcli con up netplan-wlan0-RobotWiFi` to switch back and set the hotspot profile
  `connection.autoconnect no`. Bonus: while on the hotspot the Pi shares the Mac's
  hotspot subnet, so `ssh ubuntu@172.20.10.6` (its hotspot IP) was actually the *most
  stable* path (no client isolation). Verified: `ros-humble-foxglove-bridge 3.4.2`
  installed, `DONE_RC=0`, robot back on `192.168.0.100`. **foxglove_bridge 3.4.2 is
  SDK-based → WS subprotocol `foxglove.sdk.v1`** (same as nav-trial's Jazzy 3.4.1).

## Base↔Pi discovery (the big one) — Create 3 ROS graph invisible to the Pi

- [none] **TB4 root cause, high value:** the Create 3 base's ROS 2 graph (nodes
  `/motion_control /robot_state /system_health /ui_mgr`, topics `/battery_state
  /dock_status /wheel_status /imu`, and the `/cmd_vel` subscription) was **invisible to
  the Pi** — so teleop published `/cmd_vel` but the robot never moved. `/scan` worked the
  whole time and masked it: **LiDAR is a Pi-local path (RPLIDAR→Pi→bridge→browser);
  driving needs the Pi↔base path (browser→bridge→Pi-DDS→usb0→Create 3).** Seeing the
  scan proves NOTHING about the base link.
  - **Verified fix:** the robot's `/etc/turtlebot4/setup.bash` exports
    `CYCLONEDDS_URI=/etc/turtlebot4/cyclonedds_rpi.xml`, whose `<Interfaces>` block
    restricts CycloneDDS to `wlan0` (and even with `usb0` uncommented) — and that
    restriction **blocks discovery of the base over `usb0`**. Unsetting `CYCLONEDDS_URI`
    (CycloneDDS default = all interfaces) instantly surfaced the base:
    `ros2 node list` showed `/motion_control` etc. and `/battery_state` → 0.99. Applied by
    commenting the export in `setup.bash`, restart `turtlebot4.service`, restart the
    bridge (it must inherit the fixed env too). Symptom→cause→fix all confirmed.
  - **Dead-ends ruled out (each cost a full cycle):** enabling `usb0` in the xml (no);
    `POST http://192.168.186.2/api/reboot` base reboot (no); ntpd resync (no); full Pi
    reboot with factory config (no); matching Pi/base clocks (no). The only thing that
    worked was dropping the interface restriction entirely.
  - **Clock red herring:** the Pi has no RTC and RobotWiFi has no NTP, so every Pi reboot
    resets it to a stale date (Jun 2025); the base syncs NTP *from* the Pi. Manually
    setting the Pi's clock forward created a ~13-month Pi/base skew that *looked* causal
    (docs say leases use time) but wasn't — matching the clocks did not restore discovery.
    Net: **don't reboot the Pi** (loses the clock); the base clock follows the Pi's.
  - `ros2 topic echo` of base topics returns nothing even when healthy unless you pass
    `--qos-reliability best_effort` (Create 3 publishes best-effort; Foxglove auto-matches,
    plain echo does not). And `ros2 topic pub --once` **hangs** on `/cmd_vel` (waits for a
    matching subscription the split-DDS hides) — use `-w 0`. <!-- absorbed: 2026-07-24 (ros2 1.2.0) -->

- [none] **Create 3 power (storage mode):** a **7-second** power-button hold = "storage
  mode" (disconnects the battery from robot AND payload/Pi) — **the ONLY way back on is to
  dock it**; button presses won't power it. There is no gentle button power-off; short
  press has no power function. Normal pattern is dock=on/idle, undock=drive. Proper
  shutdown = `ssh … sudo shutdown -h now` first (Pi rides on base power), then storage
  mode. Boot cue: spinning-white ring → "happy sound" (~2 min).

- [none] **Foxglove can't call ROS 2 actions** (dock/undock are actions). Working pattern:
  a tiny rclpy helper node subscribes to `std_msgs/Empty` on `/teleop/dock` `/teleop/undock`
  and fires the Create 3 `Dock`/`Undock` action goals; Foxglove **Publish panels** (topic
  publish, its most basic capability) become the buttons. Verified end-to-end (dock,
  undock, and drive all work from the browser). <!-- absorbed: 2026-07-24 (foxglove 1.3.0) -->

- [none] **`pkill -f foxglove_bridge` over SSH self-matches** the `ros2 launch
  foxglove_bridge …` command running the pkill → kills its own session (SSH exit 255).
  Kill stale bridges **by port** (`fuser -k 8765/tcp`) instead. Detached helper: launch
  with `nohup … & echo $! >pidfile` (NOT `setsid …` if you want `$!` to be the real pid). <!-- absorbed: 2026-07-24 (foxglove 1.3.0) -->

- [none] **macOS routing when wired to a no-internet robot LAN:** the Ethernet service
  outranks Wi-Fi in the service order, so the Mac sends its default route (internet) down
  the dead-end robot LAN and the browser goes offline. Fix: System Settings → Network → ⋯ →
  **Set Service Order** → Wi-Fi above the USB LAN. Directly-connected robot subnet still
  routes out the cable; internet goes via Wi-Fi. (Also: Foxglove web app needs internet to
  *load*, separate from the LAN WebSocket to the robot.) <!-- absorbed: 2026-07-24 (environments 1.4.0) -->

## Robot facts (→ architecture-brief once app exists)
- Platform: TurtleBot 4 (iRobot Create 3 base + RPi 4 + RPLIDAR + OAK-D), ROS 2 Humble,
  Ubuntu 22.04.4 aarch64, CycloneDDS, `ROS_DOMAIN_ID=0`, no namespace.
- Net: RobotWiFi Wi-Fi, robot `192.168.0.100` (wlan0, persistent), Mac `192.168.0.101`
  (en5 wired to router LAN1), router `192.168.0.1`. avahi INACTIVE (`ubuntu.local`
  won't resolve — use IP). SSH `ubuntu@192.168.0.100`, key installed, sudo pw `turtlebot4`.
- Live topics (24): `/scan /cmd_vel /tf /tf_static /battery_state /imu /joint_states
  /wheel_status /dock_status /hazard_detection /joy /robot_description /ip
  /oakd/rgb/image_raw` (+preview/camera_info). OAK-D already publishing (phase-2 head start).
- Create 3 base wired to Pi over usb0 (`192.168.186.2`). Base battery powers the Pi —
  **undocked + low battery = Pi brown-outs/reboots** (caused repeated drop-offs during
  bring-up until docked).

## Orin web-console kickoff (Foxglove self-hosting docs)
- **[find-docs] Foxglove self-hosting story changed — old open-source `foxglove/studio` Docker
  image is gone.** Expected (training data / the "just open app.foxglove.dev" habit): self-host
  by running the open-source `foxglove/studio` nginx image with `?ds=foxglove-websocket&ds.url=...`.
  Reality (ctx7 `/websites/foxglove_dev`, docs.foxglove.dev/docs/embed/self-hosted, fetched
  2026-07-24): current self-host path is `@foxglove/embed`'s `FoxgloveViewer` embedded in your own
  page — `new FoxgloveViewer({ parent, orgSlug: undefined, src: "http://localhost:8080/" })`,
  layout via `opaqueLayout` (exported layout JSON), live data via
  `viewer.setDataSource({ type:'live', protocol:'foxglove-websocket', url:'ws://robot:8765' })`.
  **The self-hosted viewer asset requires a PAID Foxglove plan** (user confirmed) → ruled out for
  the Orin console; chose the free launcher-deep-link approach instead.
- **Deep-link forms that DO work free:**
  `https://app.foxglove.dev/~/view?ds=foxglove-websocket&ds.url=ws://<host>:<port>&layoutId=<uuid>`
  (hosted; `layoutId` = a layout already imported into the user's org — there is **no**
  arbitrary-layout-URL param) and `foxglove://open?ds=foxglove-websocket&ds.url=ws://<host>:<port>`
  (desktop app; fails silently if not installed). Gotcha: `app.foxglove.dev` is `https` and the
  robot bridge is `ws://` (insecure) — Foxglove documents `ds.url=ws://...`, but some browser/OS
  combos block insecure ws from a secure origin; the desktop deep-link sidesteps it.
- Design compiled to `docs/superpowers/specs/2026-07-24-tb4-teleop-orin-console-design.md`
  (Orin phase of tb4-teleop; not a separate app).

## Orin board — prep / headless access (for the tb4-teleop Orin console phase)
Target device stood up 2026-07-24. Facts an agent picking up the Orin phase needs:
- **Hardware:** NVIDIA **Jetson Orin Nano (Super) Engineering Reference Dev Kit, 8 GB** —
  6 CPU cores, 7.4 GiB usable RAM (mind memory on heavy models), **915 GB NVMe, ~783 GB free**.
- **Software:** **JetPack 6.2** (L4T **R36.4.3**), Ubuntu 22.04.5, kernel 5.15.148-tegra.
- **Docker: GPU-ready out of the box** — Docker 26.1.3, operator user in `docker` group,
  **default runtime already `nvidia`**, nvidia-container-toolkit 1.16.2. No extra setup to run
  GPU containers.
- **Headless access (no monitor):** connect the Orin's **USB-C data/debug port** to the Mac →
  you get BOTH: (a) serial console at `/dev/cu.usbmodem*` @ **115200 8N1**, and (b) USB
  device-mode Ethernet — **Orin = `192.168.55.1`**, Mac = `192.168.55.100` (Mac iface `en6`;
  Orin bridge `l4tbr0`). SSH is open (OpenSSH 8.9, i.e. it's fully booted).
  - **Keyless SSH from this Mac is configured** (this Mac's `id_ed25519.pub` installed on the
    Orin): `ssh robium@192.168.55.1`. Username **`robium`**, hostname `ubuntu`.
    **`sudo` still needs the operator's password** (held by the operator, deliberately NOT in
    this repo).
- **No default JetPack credentials** (removed years ago, CA SB-327) — username+password are set
  at first boot; there is nothing to "look up". Ours were recovered from the operator.
- **Networking / internet:** onboard Wi-Fi `wlP1p1s0`, Ethernet `enP8p1s0`. **RobotWiFi Wi-Fi
  has no internet** (same constraint as the TB4 Pi). Got the Orin online by joining Wi-Fi to an
  **iPhone hotspot** (`nmcli device wifi connect ...` — needs `sudo`); it's saved in
  NetworkManager and auto-reconnects. **That hotspot is metered cellular — avoid multi-GB pulls
  over it** (nginx:alpine for the launcher console is ~20 MB, fine; CUDA base images are not).
  - Gotcha: two default routes coexist — Wi-Fi (lower metric → internet) + the USB link
    (`192.168.55.100`, kept for stable SSH). Both fine; don't "fix" it.
- **Ready for:** the Approach-B launcher console (nginx static host in Docker) with zero further
  board prep. GPU Docker workloads (camera/image-proc phases) also ready once online on
  non-metered internet.
