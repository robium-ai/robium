## tb4-teleop relay outage #2 — Wi-Fi drop killed the whole tunnel (control + video + mgmt SSH) [none]

**Symptom (user):** `tb4.robium.ai` showed no video stream and controls didn't work after running
overnight. Distinct from the 2026-07-26 outage (that was camera-OK / control-dead).

**Investigation (all remote, VM-side only):**
- Public site + relay VM `tb4-relay` healthy: nginx/oauth `302`, VM `RUNNING`, uptime 1d12h (no
  reboot), external IP `RELAY_IP` **unchanged** → ruled out the ephemeral-IP hypothesis.
- On the VM: **no `tunnel`-user session, nothing bound on `8765`/`8081`/`2222`** → the reverse
  tunnel was *entirely absent*, not stale. `sudo pkill -u tunnel` (last time's fix) was a no-op
  here — nothing to clear.

**Root cause (confirmed by Orin journal):** the Wi-Fi router disconnected overnight. Orin lost its
WAN; autossh logged `connect to host RELAY_IP port 22: Network is unreachable` on a loop. All
three forwards ride one outbound autossh, so control + video **+ the `2222` management route** died
together — meaning it was **not remotely recoverable** (the fix route was inside the dead tunnel).

**Fix (verified):** Wi-Fi restored → `ssh robium@192.168.0.51 'sudo systemctl restart
tb4-relay-tunnel'` forced an immediate fresh dial (autossh was still stuck on the dead socket; the
service's ServerAlive 30×3 backoff hadn't reaped it). Post-fix from the VM: forwards `8765/8081/2222`
bound, `sshd: tunnel` session live, bridge WS `101 Switching Protocols` + `foxglove.sdk.v1`, webcam
`http=200`, `2222` returns `SSH-2.0-OpenSSH_8.9p1`.

**Dead-ends ruled out:** VM reboot / IP change (uptime + natIP unchanged); VM-side stale forward
(nothing bound); Pi bridge fault (irrelevant — tunnel never reached the VM).

## go2-locomotion learn-the-stack block (code-reading, no pod) — Isaac Lab architecture + remote-GUI

Context: user resumed go2-locomotion to *understand* the stack (not new training). Cloned Isaac Lab
`3.0.0` source into `apps/go2-locomotion/reference/IsaacLab/` (git-ignored) to read the real task.

- **[isaac-lab] Where reward/cost is defined — the map a skill should hand you outright.** The MDP is
  *declared as config*, not coded. Reward AND cost live in one `RewardsCfg` (a cost is just a term with
  a **negative weight**); total step reward = `Σ weight·term()·dt`. Files:
  `…/locomotion/velocity/velocity_env_cfg.py` (the `RewardsCfg` weight table + Obs/Action/Termination),
  math in `…/velocity/mdp/rewards.py` (task-specific, e.g. `feet_air_time`) **and**
  `source/isaaclab/isaaclab/envs/mdp/rewards.py` (generic `track_lin_vel_xy_exp`, all `_l2` penalties).
  Weights are **overridden across a 3-layer inheritance chain** (`velocity_env_cfg` → `config/go2/rough_env_cfg`
  → `config/go2/flat_env_cfg`); read all three, flat wins. Two kernels only: `exp(-err²/std²)` for task
  rewards, `sum(square(x))` for penalties. Verified by reading source; the −0.5→+36 curve arithmetic
  checks out (episode 20 s ÷ dt 0.02 = 1000 steps × (1.5+0.75)·0.02 ≈ +45 gross). *Highest-value: this
  "where do I change the reward" question had no skill answer and took a clone+read from scratch.*

- **[isaac-lab] Custom robot workflow = External project, NOT a fork.** `./isaaclab.sh --new` template
  generator (doc `overview/own-project/template.rst`) scaffolds an isolated repo that `pip install -e`'s
  and imports Isaac Lab as a dependency + `gym.register`s your task. "Internal task" (editing the IL repo)
  is **only** for upstreaming a PR, and is **auto-disabled when Isaac Lab is pip-installed** (i.e. inside
  the NGC container — external is the only option there anyway). Our app is a *fourth* mode: drive a
  **built-in** task via CLI, no task code at all. Verified against 3.0.0 doc.

- **[isaac-lab] Full Isaac Sim GUI from a headless cloud pod = WebRTC livestream (exact recipe).** Isaac
  Lab AppLauncher: `LIVESTREAM=1` (public nets) / `=2` (private) + `PUBLIC_IP=<ip>`, or `--livestream {0,1,2}`;
  forces headless. Client = **Isaac Sim WebRTC Streaming Client** (separate download; macOS DMG). Ports
  (from official isaacsim docs, verified): **TCP 49100 = signaling, UDP 47998 = media** (TCP 8210 only for
  the Docker-Compose web viewer). Kit flags if setting by hand:
  `--/exts/omni.kit.livestream.app/primaryStream/{publicIp,signalPort=49100,streamPort=47998}`.
  **"opening only TCP is not sufficient — WebRTC media needs the UDP port."**

- **[isaac-lab] (dead-end ruled out, pre-emptively) VirtualGL + TurboVNC does NOT work for Isaac Sim.**
  Kit's RTX viewport renders with **Vulkan**; VirtualGL only intercepts **GLX/OpenGL** → black/software
  viewport. GPU-Vulkan-aware protocols only: WebRTC (NVIDIA built-in), NoMachine, or DCV. Saves anyone the
  classic "just install VNC" trap.

- **[none] RunPod × WebRTC risk (TENTATIVE — not yet tested on a live pod).** RunPod's HTTP proxy
  (`…-PORT.proxy.runpod.net`) is TCP/HTTP only → **cannot carry WebRTC media (UDP 47998)**. Need a
  public-IP pod with TCP 49100 + UDP 47998 exposed; RunPod's external↔internal **port remapping** may break
  WebRTC's advertised ports (signaling hands the client a port that must match). Resolution pending an
  actual provision+connect attempt — promote to a battle scar once we confirm the working port config.

- **[none] Brief path casing bug.** `docs/architecture-brief.md:206` writes `/workspace/isaaclab`
  (lowercase) while `config.py` + everything else use `/workspace/IsaacLab`. Case-sensitive on the Linux
  pod → a copy-paste `cd` would fail. One-word fix next time the brief is edited.

- **[isaac-lab] ✓ Structure reads true against 3.0.0.** Task id `Isaac-Velocity-Flat-Unitree-Go2-v0`,
  script path `scripts/reinforcement_learning/rsl_rl/train.py`, and the config-class chain all match the
  cloned 3.0.0 source exactly — `config.py`'s "re-verify, never trust across releases" posture held (no
  drift found at the *structural* level; only numeric defaults like flat `max_iterations` may differ).

**Durability gap exposed (hardening candidate, not yet applied):** the Orin's single WAN uplink is a
SPOF for *all* remote access including management. When it drops, there is zero remote recovery path.
Options to discuss: (1) an out-of-band reach to the Orin (Tailscale/cellular) independent of the
tunnel; (2) autossh already has `Restart=always` — but it can sit on a dead socket; a shorter
`ServerAliveInterval`/`ConnectTimeout` would reap faster on WAN flaps. (seen 2x: relay outage, two
different causes on consecutive days.)
